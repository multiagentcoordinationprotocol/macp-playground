# Transitive dependency lock for agents/requirements.txt.
#
# WHY THIS FILE EXISTS
# requirements.txt pins only the six direct dependencies, which leaves ~150
# transitive packages floating. A bad release of instructor, litellm or pydantic
# could then break the Docker build with no change in this repo at all, and it
# made CI's resolution gate a live-PyPI call that could fail on unrelated PRs.
# This file pins the whole closure, so both are deterministic.
#
# HOW TO REGENERATE — do not hand-edit, and do not use a clean venv
# The image installs with `pip3 install --break-system-packages` against Debian's
# SYSTEM python, so /usr/lib/python3/dist-packages participates in resolution. A
# venv-generated file would not match what actually installs. Regenerate inside a
# container matching the Dockerfile's base:
#
#   docker run --rm -v "$PWD/agents/requirements.txt:/tmp/req.txt:ro" -v /tmp/out:/out \
#     node:26-slim bash -c '
#       apt-get update -qq && apt-get install -y -qq --no-install-recommends \
#         python3 python3-pip python3-venv gcc python3-dev libffi-dev
#       pip3 install --break-system-packages --dry-run --report /out/report.json -r /tmp/req.txt'
#
# then emit `name==version` for every entry of the report's `install` array.
#
# Regenerate whenever requirements.txt changes. Note this pins macp-sdk-python
# exactly, so a new patch release inside its `>=0.9.1,<0.10` range needs a
# regeneration to be picked up — that is the intended trade for reproducibility.
#
# Generated against: Python 3.13.5, Debian 13.7 (trixie), node:26-slim.
# 155 packages. langchain (the meta-package) is deliberately absent — no worker
# imports it; see the note in requirements.txt about the openai hold.
#
# `packaging==25.0` is the one entry NOT produced by the generator, and it is the
# reason the generation command alone is not sufficient. Debian's python3-pip
# pulls in python3-packaging, so `packaging` is already satisfied when this file
# is generated and never appears in pip's `install` report — leaving it the single
# unpinned member of a 155-package closure. That matters because the CI gate runs
# with `--ignore-installed`: it ignores Debian's copy and resolves `packaging`
# fresh from PyPI (26.3 as of this writing), so gate and image were checking
# different closures, and a future `packaging` major could redden CI with no repo
# change at all. It is pinned to 25.0 — the version the base image actually
# carries — rather than to the newest, so the gate checks what ships. Debian
# already satisfies it, so this pin changes nothing about the built image.
# If you regenerate, re-add this line: the generator will not emit it.
