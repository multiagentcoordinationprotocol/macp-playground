# Policy Rule Schema Validation (GitHub issue #81)

## Context

Issue #81 is a heads-up from the spec repo (`multiagentcoordinationprotocol/multiagentcoordinationprotocol`): three merged PRs tightened what counts as a valid governance-policy `rules` object, admission-time only (RFC-MACP-0012 §8: a stored policy is evaluated under the `schema_version` it declares at replay time, so nothing already stored becomes unreplayable — only *new* descriptor admission is affected):

1. Every object level in all five per-mode rule schemas (`decision`, `quorum`, `proposal`, `task`, `handoff`) is now closed with `additionalProperties: false`, except `voting.weights` (its **keys** are participant identifiers, not fixed fields — though its **values** are still validated: `exclusiveMinimum: 0`, and the map itself has `minProperties: 1`, unconditionally, at every `voting.algorithm`) and the reserved annotation namespace `^[_$]` (e.g. `$comment`, `_note`), legal at every closed level.
2. `schema_version` is now a closed enum `{1, 2, 3}` (was `minimum: 1`, unbounded) — enforced at the **descriptor** level (`macp-policy-descriptor.schema.json`), which validates the whole `{policy_id, mode, schema_version, description, rules}` document, not a bare number.
3. `authority: "designated_role"` with an empty/missing `designated_roles` array is now rejected in all five modes (previously enforced only in Decision mode).

This repo just finished `plans/absorb-runtime-v0.8.0.md` Phase 2, which migrated all 6 `policies/*.json` files to `schema_version: 3` and fixed a `designated_role`/`designated_roles` singular-vs-plural typo bug in `src/contracts/policy.ts:22` and `src/policy/policy-loader.service.ts:92-99` (guarded by `src/policy/policies-on-disk.spec.ts:59-63,79-86`). A research pass this session, and a full independent verification pass against the code afterward (including compiling the real upstream schemas with `ajv/dist/2020` and running all 6 shipped files through them), confirmed and extended that picture:

- **Items 2 and 3 are already handled for the 6 shipped files** — verified directly. All six declare `schema_version: 3`; the one file using `designated_role` authority (`policy.lending.conservative.json:29`) has a correctly-spelled, non-empty `designated_roles`.
- **Item 1's worst-case exposure doesn't apply here**: nothing in this repo programmatically constructs, deep-merges, or template-overrides a `rules` object. The only writable-by-template/user surface is `PolicyHints` (`src/example-agents/runtime/policy-strategy.ts:3-13`) — a separate, camelCase, playground-local projection that is never sent to the runtime and is not governed by the upstream rule schemas. The only ingress for `rules` is the 6 static JSON files.
- **What's genuinely open**: this repo has **zero schema validation of `rules` at any tier** — `PolicyLoaderService.ensureLoaded()` does a bare `JSON.parse(...) as PolicyDefinition` cast (`src/policy/policy-loader.service.ts:117`), its hand-rolled `validatePolicy()` (`:39-102`) never enumerates keys, and `PolicyRegistrarService.toDescriptor()` forwards `JSON.stringify(policy.rules)` unexamined (`src/policy/policy-registrar.service.ts:211`). A `veto_threshhold: 3` typo — the issue's own motivating example — would load, register, and silently misbehave today with zero warnings anywhere in this repo's four test tiers.
- **A real, already-live conformance failure the issue itself doesn't mention, confirmed by actually compiling the real upstream `decision-rules.schema.json` against all 6 shipped files**: 3 of 6 (`policy.default.json:12-13`, `policy.claims.majority.json:13-14`, `policy.fraud.supermajority.json:13-14`) fail `objection_handling.veto_threshold: 0 must be >= 1`. This repo's own local check is what caused it — `policy-loader.service.ts:74-80` only warns when `veto_threshold` is *set and non-zero* while `critical_severity_vetoes` is false, so authors converged on `0` as the "off" sentinel. Confirmed: **omitting** the key entirely satisfies both the local check and the real schema (the schema defaults it to `1`, unread, exactly as this repo's own design already intends). This is exactly the kind of bug a *real* upstream schema catches and a hand-authored one would not — the TS `PolicyDefinition['rules']` type is itself narrower than the upstream schema (missing `voting.algorithm: 'plurality'`, `objection_handling.critical_objection_action`, `commitment.allow_decline_over_approval`, and incorrectly requiring `veto_threshold` where the schema makes it optional), so deriving a hand-written ajv schema from it would have reproduced this same gap.
- **Feasibility of validating against the real schema**: the actual upstream schemas exist locally at `/Users/Shared/multiagentcoordinationprotocol/multiagentcoordinationprotocol/schemas/json/policy/{decision,quorum,proposal,task,handoff}-rules.schema.json` **plus** the descriptor schema one level up at `/Users/Shared/multiagentcoordinationprotocol/multiagentcoordinationprotocol/schemas/json/macp-policy-descriptor.schema.json` (sibling checkout, remote `multiagentcoordinationprotocol/multiagentcoordinationprotocol`, HEAD `4f15b96cac6e39d62925a5baa1ef80a42c2f818d`, all three #81 commits present and confirmed: `178afe7`, `18a38a7`, `6f300c8`) — but this repo has no submodule, npm package, or fetch step pulling them in, and CI cannot depend on a sibling checkout existing (confirmed: `macp-sdk-typescript@0.11.0` ships no schemas; the sibling's only published package, `@multiagentcoordinationprotocol/proto`, ships no JSON schemas either). The only route that keeps CI green offline while validating against the *real* schema is to **vendor** copies into this repo with a provenance note — confirmed there is no lower-cost alternative already available.

## Long-term posture

- **Not a one-way door.** Vendoring the schemas is easy to reverse (delete `schemas/policy/`, remove the validator, revert the loader wiring) and adds no external runtime dependency — ajv is already a direct dependency of this repo. Nothing here changes a public contract; `PolicyDefinition`'s widening is purely additive.
- **Staleness debt, now cheaply mitigated rather than fully accepted.** `schemas/policy/` is a manually-triggered vendor copy, not a submodule or a build-time fetch — but Phase 1 now includes a `schemas:sync` script plus a **non-blocking** CI drift check, so staleness is surfaced automatically instead of silently accumulating, at near-zero infrastructure cost (confirmed: no submodule, package, or fetch mechanism already exists to build on instead — this is the cheapest available option, and it's cheap enough to include rather than defer). What remains genuinely deferred: nothing *enforces* a re-sync — a human still has to act on the drift signal. That's an appropriate stopping point for a demo-scoped service (`CLAUDE.md`: "intentionally a demo/showcase service, not a production system boundary").
- **The registrar gap is real but explicitly out of scope.** `PolicyRegistrarService` has no pre-flight validation and a `failed_precondition`-based heuristic (`isReadOnlyRegistryError()`, `:226-238`) that could misclassify a genuine schema-rejection from the runtime as "registry is read-only" and silently downgrade to verify-only mode. This phase's work substantially *reduces* the odds of hitting that path (a shape-invalid policy is now caught locally, with a loud warning, before registration is attempted) but doesn't eliminate it for other `failed_precondition` causes. Worth its own follow-up issue if ever observed in practice; not addressed here because #81 is scoped to validation, not registrar error-handling semantics.

## Enterprise concerns

- **Reliability:** the loader's fail-open-with-warning design is preserved throughout — this plan raises the bar for what counts as "clean" without changing what happens when a policy isn't. The one true hard gate is CI (`policies-on-disk.spec.ts`), appropriately scoped for a demo-service-scale project.
- **Observability:** no change to logging/metrics surfaces beyond what `PolicyLoaderService`'s existing `Logger.warn` already provides — the new validator's findings flow through the same warning channel.
- **Security:** none of this touches an auth boundary or trust boundary — `rules` shape validation is a correctness concern about governance-policy authoring, not a security control.
- **Test coverage floor:** flagged explicitly in Phase 2 (AC #5) — the new validator file and loader changes count toward this repo's enforced Jest coverage thresholds (`jest.config.ts:20-27`); confirmed as an explicit acceptance criterion rather than left implicit.

## Open questions

- **`mode: "*"` validated against the Decision schema — UNCONFIRMED.** Chosen because it's this repo's only rules shape in practice today (every scenario pack uses `macp.mode.decision.v1` exclusively) and is cheap to reverse (a one-line dispatch change in `PolicyRulesValidator` if it's ever wrong). Blast radius if wrong: `policy.default.json` would validate against the wrong schema and either false-pass or false-fail — caught immediately by Phase 2's CI gate, so the blast radius is a build failure, not a silent runtime issue. Logged to `ASSUMPTIONS.md` (see this worktree's own copy) as `UNCONFIRMED`, for `/reconcile` to close out later.
- **Which hand-rolled `validatePolicy()` checks are redundant with the vendored schema — now resolved, not deferred.** The prior draft of this plan left this for implementation time; a full line-by-line check against the vendored schema during this plan's own verification pass confirmed exactly 4 checks are redundant (supermajority threshold, weighted-weights, minimum_confidence range, designated_role) and exactly 1 is intentionally stricter-than-upstream (veto_threshold-when-vetoes-on) — see Phase 2's Delivers for the full accounting. No longer an open question.
- **The `critical_severity_vetoes: true` requiring an explicit `veto_threshold >= 1` check being stricter than upstream (which defaults it to `1`) — kept deliberately, not escalated.** A "consequential but decidable" call: the stricter local check costs nothing (it only ever fires on a case that's also schema-legal either way) and improves policy-file clarity by making an implicit default explicit. Decided by Opus, recorded in Phase 2.
